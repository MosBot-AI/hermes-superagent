# 95. 只读规范记忆修改结果

[English](95-canonical-mutation-status.md) | 简体中文

## 范围与价值

[Issue #131](https://github.com/MosBot-AI/hermes-superagent/issues/131) 为可信本地 [Memory SDK](85-local-memory-sdk-zh.md) 增加可选的只读结果检查操作。中断的 `remember`、`correct` 或 `forget` 可能已经提交，即使调用方没有收到可用确认。检查允许调用方使用事先保留的请求元数据恢复规范回执，无需重新提供原文，也无需再次执行修改。

现有 SQLite 存储仍是权威来源。这是 API-v1 的增量能力，不新增 schema 迁移、数据库、provider 选择或原生生命周期钩子。仅支持 CRUD 的适配器仍可使用。不会通过新的原生命令、模型工具或 REST 路由暴露该操作。Hermes 兼容性固定版本仍为 `2281116525106e3c109993ccb5dc74d02bfc1427`。

这个结果基础操作是未来来源接受的前置条件。它不接受来源、不授予保留权限、不推进任何游标、不启用自动采集，也不声明原生 checkpoint-v2。[来源回执提案](94-receipt-source-reads-zh.md) 仍然隔离且未激活；原生来源回执不是规范记忆回执。父项 #43/#45 保持开放。

## 写入前绑定原始请求

`mutation_request_identity(operation, payload)` 是面向三种规范记录修改的纯函数。它采用与后端完全一致的规则验证并规范化请求，然后仅返回 `operation`、`request_id` 和 `expected_digest`。摘要为 `[operation, normalized_request]` 现有紧凑、按键排序、保留 Unicode 的 JSON 编码的 SHA-256。历史摘要语义不变：保留默认 topic 处理，省略的 expiry 不会被静默转换成显式 null。

在提交获准修改之前，私密保留这些元数据。后续 `mutation_receipt_status` 请求就是这个精确身份对象。它不包含原文、topic、来源文本、namespace 选择器、路径、URL 或 SQL。元数据和摘要不是匿名数据、身份认证、capability token，也不授予读取其他配置档案的权限。可信打开方仍负责当前 namespace 和读取准入。现有 SDK 准入仍会执行有界 export 检查，并可能在调用此操作之前读取一条记录载荷；仅含元数据的保证适用于状态调用本身，而非整个 SDK 生命周期。此辅助函数不会替调用方持久保存恢复日志。

分发前会检查可选的 `mutation_receipt_status` 能力。缺少该能力的适配器必须显式拒绝。操作只读取已经绑定的存储，不发现其他存储、不创建缺失存储、不迁移只读存储，也不回退到另一个后端。

## 分开解释历史与当前结果

SDK envelope 的 `replayed` 始终为 false，因为检查是一次新读取，而非修改重放。两种成功状态都包含 `evaluated_at`，即本次读取的规范 UTC 秒级时间戳。

- `state: committed` 包含历史六字段修改回执 `receipt`（`record_id`、`revision`、`status`、`operation`、`request_id`、`event_sequence`），以及单独的 `current` 对象（`record_id`、`revision`、`status`、`expired`）。两者在同一个规范存储 SQLite 快照中读取。到期状态在该快照读取时评估；`expired` 不代表之后读取的状态。
- `state: absent_at_snapshot` 不包含回执或记录元数据。经过验证的该快照未观察到匹配请求。写者仍可能随后提交，因此不存在不是发起新键请求的许可，也不证明中断的尝试永远无法完成。
- 相同请求键对应不同摘要或操作时，以 `idempotency_conflict` 失败，不泄露已存摘要或回执。
- 存储失败、格式错误证据，或不一致的回执/事件/记录关系都会安全拒绝，不会成功返回不存在。SDK 按情况报告已脱敏的读取错误（`backend_failure` 或 `invalid_result`），绝不透传任意后端异常文本。

历史 `remember` 回执在更正、到期或遗忘之后仍可能写着 `active`。只有独立的当前元数据描述本次读取快照中的记录。检查绝不恢复内容、改写回执或撤销抑制。已提交回执证明后端的历史修改边界，不证明当前来源可用性、事实真实性、模型召回资格、送达或其他行动的权限。

内置后端在现有读取事务中验证有界元数据及回执/事件/当前记录关系。扫描最多接纳 1,000 条记录、11,000 个事件、12,000 行回执（包括既有到期清理批次回执），以及 10,000 个非终止事件。规范回执 JSON 限制为 2,048 个字符；既有清理批次 envelope 在取回前限制为 16,384 字节。这些内部批次接受兼容性验证，但不会作为新的状态操作暴露。报告不存在之前会检查所有关联，避免已提交事件丢失回执后被误认为请求未提交。此操作不会选择记录的 content、topic、source 或 session 标签。严格 SDK 验证检查精确字段、标识符、整数和布尔类型、请求的操作/键、历史至当前 revision 与终止状态关系，以及不存在结果的结构。通过验证不能发现伪造了表面一致证据的恶意适配器；经过审查的进程内适配器仍是可信代码。

## 恢复与隐私边界

若写入确认丢失，重新打开同一个可信存储并检查已保存的身份。不要自动重复修改、更改请求键，或将下游来源标为已处理。在实际写者结果及任何后续行动的授权与结果确定之前，失败或不存在仍应保持未解决。本操作自身不进行重试，不改变记录、事件、回执、来源抑制或消费者游标。

受支持的本地存储不防范恶意原始数据库编辑、伪造适配器、手工替换或旧备份恢复。快照检查不为后续独立写入提供发布栅栏。读取事务结束后，已经返回的结果可能立即变为历史观察。哈希绑定和匹配的记录 ID 均不构成跨库原子性。

仅返回有界元数据。标识符及请求哈希仍须私密处理。现有回执保留方式不变；检查不承诺安全擦除旧数据库页、日志、备份、导出或已经交付到其他位置的副本。

## 验证与仍待完成的接受协议

`personal_agent.memory_conformance` 中单独的可选 `run_mutation_status_conformance(factory, isolated_synthetic=True)` 运行器使用调用方拥有的空白合成存储，且与 CRUD/进度/检查点套件使用的存储分开。它有意写入自有夹具；只有状态操作是只读的。运行器覆盖该能力在重开、已提交/不存在观察、请求变化冲突、历史更正及终止性遗忘中的行为。测试还覆盖无效适配器和存储、只读操作、确认丢失、COMMIT 前后的进程突然退出，以及确定性的并发更正/遗忘。按[执行流程](github-project-workflow-zh.md) 运行仓库完整检查和固定原生契约；PR 记录实际执行数量和精确提交 CI。测试存在本身不代表通过或生产验收。

未来与来源绑定的接受仍需诚实的出处、明确的保留/接受权限、在规范写事务内部核查的来源身份及抑制、持久决策结果，以及单独定义的来源消费游标。现有 `consumer_advance` 跟踪调用方声明的本地**记录事件**进度；原生行 ID、回执日志序列号和未来接受队列不能与它互换。来源游标不得跳过已经准入但尚未解决的决策，也不得暗示所有原生历史都已处理。

若承诺原生来源在规范发布完成前始终有效，就需要经过证明的宿主/发布栅栏。仅在写入前再次检查来源不足以保证这一点。另行获准保留的快照可以改用明确的导入语义，同时清楚说明后续原生转录删除本身不会遗忘规范记忆。该模式仍须遵守规范更正与遗忘，不能伪造当前输入候选路径，也不能满足严格的当前来源有效性门禁。此处不实现该接受模式或栅栏。原生来源、规范记忆及后续消费者记账继续保留各自独立的提交边界。
