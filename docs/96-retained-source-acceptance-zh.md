# 96. 显式接受保留的来源快照

[English](96-retained-source-acceptance.md) | 简体中文

## 已实现的边界

后续的[显式保留观察来源](98-observed-source-retention-zh.md)以独立、如实标记的 `observed_native_snapshot` 来源增加原生 LOCAL 命令及 schema-13 迁移。下文描述 #133 的回执路径和共享接受协议；其旧来源、摘要与历史输出保持不变。“不是原生命令”仅描述原始 #133 切片，不适用于新增的 #137 命令。

[Issue #133](https://github.com/MosBot-AI/hermes-superagent/issues/133) 新增实际的规范 SQLite 接受操作，用于接受明确保留的原生原始来源。这是 Memory SDK API-v1 的可选操作族，包含 schema-12 可写迁移，以及一个读取[回执绑定来源提案](94-receipt-source-reads-zh.md)的隔离可运行消费端。它不是自动摄取、新模型工具、原生命令、HTTP 路由、宿主采纳、安装或生产启用。宿主兼容性固定版本仍为 `2281116525106e3c109993ccb5dc74d02bfc1427`。

可信本地操作员必须另外授权将选定来源作为独立快照保留，并选择规范记忆的保留方式：明确的 `expires_at` 时间戳或明确的 null。必填的 `retention: independent_snapshot` 字段记录这种导入语义，但不认证用户，也不会把模型载荷变成许可。SDK 绑定和规范写入端都要求现有的 `explicit_local_operator` 路径。模型绑定和只读写入端不能借用这种权限。经审查的进程内 Python 仍是可信代码，不是防范伪造来源或绑定的沙箱。

## 来源仍然只是证据

隔离消费端从回执绑定的原生读取快照中读取一个精确的原始行。它不会把压缩摘要当成直接来源，也不会导入整段对话。选中的内容必须符合现有规范记录的 2,048 字符上限。导入保留原始 `user` 或 `assistant` 角色、精确内容指纹、稳定来源身份和原生回执身份。来源身份独立于接受请求键、消费端 ID 和回执尝试，因此更换这些值不会把同一个原始来源变成新来源。

规范记录现有的 `source` 字段仍表示最近的编辑路径，即 `explicit_local_operator`；它从未代表不可变的原始作者身份。另行保存的不可变决定来源标记使用 `kind: retained_native_snapshot`，并保留原始角色和来源元数据。通过 `source_status` 可同时查看这些信息及规范记录的当前修订、状态和到期信息。用户角色行、匹配子串、指纹或成功回执都不能证明事实真实性、经过验证的人类作者身份或权限。导入文本始终是不可信证据，进入召回时也不例外。

来源指纹是精确 UTF-8 内容的 SHA-256，与现有当前输入候选的抑制方式一致。空白或内容发生变化会产生不同的精确指纹。这不是语义去重、匿名化、秘密存储或完整的人员/来源身份解析。可信调用方必须绑定正确的原生存储和配置档；任意来源元数据都不是查询 API，也不能授权打开其他存储。

## 先保留一个待处理槽，再实际接受

可选能力为 `retained_source_acceptance`。现有仅支持 CRUD 的适配器保持兼容，并明确拒绝不支持的操作。这里没有增加动态适配器加载器、提供方选择或 REST 契约变更。

1. 准备完整导入请求，并在准入前保留纯函数 `source_request_identity` 的结果。规范化摘要绑定内容、主题、明确的保留方式、来源信息、消费端、预期来源序号和请求键。身份对象仅包含键和摘要，不包含原文，也不授予权限。
2. `source_stage` 持久保留该消费端的下一个槽。仅存储有界元数据和请求摘要；暂存表不再复制内容、主题或会话标签。暂存不创建规范记录/事件，也不推进游标。每个消费端只能有一个未解决槽。只要该槽仍待处理，就拒绝第二个请求键，重启后也是如此。
3. `source_accept` 必须与已经暂存的请求完全一致。在规范存储的 `BEGIN IMMEDIATE` 写锁内，它检查来源抑制，创建规范记录/事件/回执，记录保留来源的谱系，并解决该槽。来源游标与同一个规范提交一起推进。它不会复用当前输入候选路径，也不会伪造候选锚点。
4. `source_discard` 明确解决精确的待处理键/摘要，而不创建记录。它抑制这个精确来源指纹，并清除匹配的当前输入待审草稿。丢弃决定保持终态，并推进这个消费端的来源游标。它不是自动跳过，也不是取消另一个进行中的写入端。
5. `source_status` 读取已保存的精确键/摘要，不重放变更，也不需要来源文本。`source_cursor` 报告该消费端已完成的序号以及任何待处理槽。使用受支持的现有只读打开方式时，两者都不创建、迁移或写入存储。

所有决定和抑制元数据都会保留，最多 1,000 个决定、64 个消费端，不静默淘汰。上限拒绝新的准入；现有接受、丢弃和规范遗忘不需要另外分配决定/抑制空间。仅含元数据的待处理槽不会自动到期，也不会按超时释放。调用方负责保管完成接受所需、已授权保留的载荷，也可以明确丢弃无法完成的槽。

## 三种不同的进度域

来源游标是这个消费端明确准入的决定的连续序列，每个决定都由接受或丢弃解决。它从同一规范事务中经过验证的持久行推导；待处理行会阻止后续准入。它不是原生行 ID、原生回执日志偏移、规范记录事件游标，也不衡量全部原生历史。普通 `remember`、`correct` 和 `forget` 不推进它。现有 `consumer_advance` 仍用于本地记录事件记账，不能解决来源槽。

状态不存在只表示在被检查快照中不存在。较早的准入尝试仍可能稍后获得写锁。必须保留并对账原请求键，不要把不存在解释为可以替换请求键或来源。这里强制保证的待处理槽语义始于已提交的准入，而不是尚未观察到的调用方尝试或网络请求。

## 重试、更正与遗忘

完全相同的暂存重试观察已有决定。已经接受/丢弃的精确重试返回历史决定回执，不另建记录，不重复推进游标，也不恢复载荷。同一键下更改请求内容、来源、保留方式或序号会产生幂等冲突。对已经准入的来源身份使用不同键会被拒绝。创建谱系之前会检查内部规范回执键是否冲突，防止把无关历史记录悄悄改标为新来源。

规范更正和遗忘在同一个写事务中标记保留来源抑制，并删除匹配的当前输入待审草稿。接受在其写事务内同时检查保留来源和当前输入抑制。新请求键、消费端或原生回执不能绕过精确来源身份/指纹抑制。抑制容量已由现有决定行保留，因此准入配额用尽不会阻止遗忘。规范保留清理使用相同的终态遗忘路径。

`source_status` 把历史决定的原始 `remember` 回执与当前规范元数据分开。旧的接受回执仍可能显示 `active`，但当前记录已更正、到期或遗忘。状态操作不暴露记录内容、主题或会话标签。指纹和标识符仍需要私密处理。SDK 构造仍执行常规的有界导出准入检查，可能读取载荷；仅元数据保证适用于来源状态/游标操作，而非 SDK 的整个生命周期。

## 独立存储与隐私限制

原生来源读取/回执、规范准入/接受，以及调用方持有的保留载荷具有独立生命周期。本实现不声称分布式事务，也不声称原生来源在规范发布前一直保持有效。独立授权的快照可以在原生对话后来删除后被接受。该删除不会自动遗忘其规范记录；适用时，操作员必须使用规范更正/遗忘。反过来，规范遗忘不会擦除原生对话行、历史备份、导出、调用方保管的载荷或已经返回的模型上下文。

隔离消费端和测试使用仅供审查的宿主提案。它们不会修改已安装宿主、启用 checkpoint-v2、安装/激活提供方或调用模型。自动来源选择、后台提取、完整原生来源覆盖、要求来源当前有效的模式所需的发布屏障，以及 #43/#45 的完整验收仍未完成。原始数据库修改、恶意 Python 适配器及用旧备份替换文件不在受支持的完整性边界内；元数据验证是失败关闭的证据检查，不是防篡改存储。

## 验证

可选的 `run_retained_source_conformance(factory, isolated_synthetic=True)` 套件使用专用空合成存储，测试实际暂存/接受/丢弃、重新打开、独立游标行为、历史重试和遗忘。单元测试覆盖 SDK 能力/作用域准入、有界畸形请求/结果、规范抑制、迁移、事务失败、COMMIT 前后的真实子进程退出及并发写入。隔离来源提案测试使用真实的原生与规范 SQLite 存储，包括明确授权捕获后删除来源的场景。

请运行[开发检查](../README-zh.md#开发验证)和来源提案的独立测试入口。PR 记录实际执行数量、精确提交、独立审查和包证据。测试文件存在本身不代表通过、生产发布或完整原生生命周期验收。
